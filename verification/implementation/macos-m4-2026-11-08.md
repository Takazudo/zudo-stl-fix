## Interactive acceptance (packaged app)

The archive was extracted with `ditto -x -k` to
`~/zudo-accept 受入 テスト/2026-11-08 M4 受入/アプリ 置き場/zudo-stl-fix.app` and launched with
`env -i HOME=… PATH=/usr/bin:/bin open -a`. The app process ran from that path with
`PATH=/usr/bin:/bin` and created `$TMPDIR/zudo-stl-fix-<UUID>`. Inputs were copies under
the same root. The repository fixtures were never opened by the app.

**Method.** Controls were driven through the Accessibility API (`AXPress`), System
Events keystrokes, and ⌘⇧G with pasted paths in the native panels. Finder
drag-and-drop used real `CGEvent` drags from a Finder window onto the drop zone.
Before each drag, a guard checked that the source and drop points were topped by
the intended windows (see "Test-harness incident"). State was read back from the
AX tree, the file system and window-only screenshots. The system was in dark
appearance at the start.

## Defects found and changes made

No regression was found. Nothing in `app/`, `engine/`, `packaging/`, `scripts/`,
`fixtures/` or `Makefile` was changed.

One long-standing engine classification issue surfaced. A truncated binary STL can
be reported as a resource-limited ASCII file instead of malformed input. The outcome
is still non-success with no Save, but the message is wrong. The behavior dates from
`caa79f3`, reproduces with the portable worker, and is not native-specific. It is
tracked as #30 under #22 and was not changed in this milestone.

## Observations, not changed

- The **Details** sheet sizes to its text and becomes larger than the 760×560 main

  VoiceOver all work.
- The secondary-style reason line under refused and error rows uses the system

  in dark). The status lines and warnings above it meet the ≥5:1 values listed earlier.

## Test-harness incident (no product impact)

My first Finder drag was unguarded. Activating Finder raised all of its windows,
so another Finder window covered the app, and the drop moved the five generated test copies from
`names 名前/` into that window's folder. They were moved straight back with `mv -n`
and verified by content (`cmp` against their fixture sources). Nothing else in that
folder was touched. Every later drag used a guard that checks the topmost window at
both points before and during the drag and returns to the source if the check fails.
