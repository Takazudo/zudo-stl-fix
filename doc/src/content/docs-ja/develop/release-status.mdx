## リリースは GitHub Releases で公開しています

アプリは [GitHub Releases](https://github.com/Takazudo/zudo-stl-fix/releases) で `zudo-stl-fix-<version>-macos-arm64.zip`（macOS 27 以降、Apple silicon のみ）と `.sha256` ファイルとして公開しています。ビルドはすべてローカルの Apple silicon Mac で行います。`scripts/build-macos.sh` は開発用のビルドを作り、`scripts/release-macos-local.sh` はリリース用のアーカイブを作って GitHub Release の下書きに添付します。リポジトリの Claude Code スキル `/l-make-release` が、バージョン決定、ビルド、下書き、リリースノート、公開、検証までの流れ全体を実行します。[継続的インテグレーション](./ci.mdx)を参照してください。

これらのアーカイブはアドホック署名のみで、Developer ID による署名も公証もされていないため、初回起動時に Gatekeeper が確認を求めます。開発環境で起動できたからといって、ダウンロードしたコピーが Gatekeeper を通過する証拠にはなりません。

## Developer ID での配布に向けて残っている作業

Developer ID による公開向けの署名と公証は、別途承認が必要な作業です。リポジトリのスクリプトでは、認証情報を使った署名は一切有効になっていません。将来の署名付きリリースの手順では、次のことを行う必要があります。

1. 署名用 ID、Team ID、公証用プロファイルを非公開の設定として受け取る。
2. ネストされたコードを内側から順に、必要な Hardened Runtime の設定で署名し、最後に外側のアプリに署名する。
3. 公証し、ステープルする。
4. ダウンロードした生成物を Gatekeeper でテストし、ネストされた署名と初回起動を確認する。
5. 同梱する依存関係について、ライセンスとソース公開の義務を確認する。

:::warning
ユーザーに対して、quarantine 属性をまとめて削除する、Gatekeeper を無効にする、管理者権限でアプリをインストールする、といった指示は決してしないでください。
:::

リリースの検証は、Release が公開されたときにだけ `release.yml` で行います。日々のコミットでは、ネイティブのビルド、公証、完全なパッケージングは実行しません。
