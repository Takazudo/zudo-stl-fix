## Summary

As of 2026-11-08, the supported platform is **macOS 27 or later on Apple silicon (arm64) only** (owner decision; see `docs/ACCEPTANCE.md`). The packaged app has passed the native package gate and the full interactive acceptance matrix, including a live VoiceOver pass, on two arm64 Macs: an **Apple A18 Pro on macOS 27.2** and an **Apple M4 on macOS 27.0.1**. [Issue #1](https://github.com/Takazudo/zudo-stl-fix/issues/1), which tracked deferred native verification, is closed, and no platform verification is pending. Older macOS versions and Intel x86_64 are not supported, so they are not verification targets.

The evidence is in [`verification/implementation/`](https://github.com/Takazudo/zudo-stl-fix/tree/main/verification/implementation) in the repository.

:::warning
A validated mesh is not proof of printability, fit, wall thickness, or strength. None of the results below mean "print ready".
:::

## Fixes verified after the acceptance runs

- A truncated binary STL is now reported as **Error** with `invalid_input` and a reason that says it is truncated ([issue #30](https://github.com/Takazudo/zudo-stl-fix/issues/30)). The M4 run had shown it as **Check incomplete** with a misleading reason; it was already never a success.
- Repairs of files with very long names can now be saved. The stem is shortened when the destination filesystem cannot hold the name ([issue #34](https://github.com/Takazudo/zudo-stl-fix/issues/34)). See [Saving](../app-guide/saving.mdx).

Both were rechecked natively on macOS 27.

## History

The records below are kept as history. At the time, the proposed floor was macOS 14 and x86_64 was still planned. Both were dropped on 2026-11-08.

### 2026-11-07, Apple A18 Pro, macOS 27.2

On 2026-11-07, two builds passed the package gate and broad Finder/UI acceptance: Finder drag-and-drop, the open panel, per-file and batch save, read-only destinations, cancellation, quit, stale-workspace cleanup, light and dark appearance, and resizing. That run found and fixed missing failure reasons and the **Choose Files…** accessible name.

### 2026-10-16, macOS 26.6.2

Recorded on 2026-10-16 on macOS 26.6.2, arm64, Xcode 27.0, Apple Swift 6.4, CPython 3.12.14.

| Check | Result |
|---|---|

| `make test-worker` | 41 passed |

The resulting archive is ad-hoc signed, not notarized, and not released.

Interactive checks that were performed on the relocated app: launch from a path with spaces and Japanese characters; opening all 11 originals via `open -a`; one window; the nine healthy originals show **No repair needed** and both defective rails show **Repair ready** with the tiny-triangle warning visible; Save controls enabled only for those two; the quit-with-unsaved-repairs confirmation; stale workspace cleanup after a forced kill; fixture hashes unchanged.

#### Defects found and fixed

Running the real app found two defects that unit tests missed: every file failed because a `/private` path prefix was stripped before it reached the worker, and every Finder-opened file created a new window. Both are fixed and covered by tests.

#### Not exercised on 2026-10-16 (later resolved)

These were not exercised at the time, because the session had no Accessibility permission to drive the UI. The interactive items were later passed on macOS 27 arm64; the macOS 14 floor and x86_64 were dropped from support instead:

- Finder drag-and-drop onto the window.
- The save panel, per-file and batch, and independent re-verification of saved STLs.
- Read-only destinations and name collisions in the UI.
- Active and queued cancellation in the UI.
- Details and JSON report export, and Reveal in Finder.
- Keyboard access, VoiceOver, light appearance, and resizing.
- The macOS 14 floor, which was not runtime-tested; only the host OS was exercised.
- x86_64.

At that point, saving, collision, permission, and cancellation logic was covered by Swift tests only. The full checklist is in `docs/ACCEPTANCE.md`.
