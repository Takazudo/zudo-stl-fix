## Releases are on GitHub Releases

The app is published on [GitHub Releases](https://github.com/Takazudo/zudo-stl-fix/releases) as `zudo-stl-fix-<version>-macos-arm64.zip` (macOS 27 or later, Apple silicon only) with a `.sha256` file. Every build is made on a local Apple silicon Mac: `scripts/build-macos.sh` makes development builds, and `scripts/release-macos-local.sh` makes the release archive and attaches it to a draft GitHub Release. The repository's `/l-make-release` Claude Code skill runs the whole flow (version, build, draft, notes, publish, verification). See [Continuous integration](./ci.mdx).

These archives are ad-hoc signed only: not Developer ID signed and not notarized, so Gatekeeper asks for confirmation on first launch. A development launch is not evidence that a downloaded copy would pass Gatekeeper.

## What Developer ID distribution would still need

Public Developer ID signing and notarization is a separately authorized task, and no credential-based signing is enabled in the repository scripts. A future signed release process should:

1. Accept the signing identity, Team ID and notarization profile as private configuration.
2. Sign nested code from the inside out with the needed hardened-runtime settings, then sign the outer app.
3. Notarize and staple.
4. Test the downloaded artifact with Gatekeeper, and verify nested signatures and first launch.
5. Review licence and source obligations for the shipped dependencies.

:::warning
Never instruct users to remove quarantine wholesale, disable Gatekeeper, or use administrator access to install the app.
:::

Release verification runs in `release.yml` only when a Release is published. Daily commits do not run native builds, notarization, or full packaging.
